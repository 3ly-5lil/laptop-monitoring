# Logs Dashboard — Conversation Summary

## Context

The monitoring stack uses:

- Grafana for dashboards
- Loki for log storage/querying
- Grafana Alloy for collecting systemd journal logs
- Prometheus and exporters for metrics elsewhere in the observability stack

The goal was to build a **Logs / Troubleshooting** Grafana dashboard focused primarily on log exploration rather than graphs.

---

## Problem / Requirement

The desired dashboard should provide:

1. A main **Log Explorer** showing recent journal entries.
2. Summary statistics for:
   - Errors
   - Warnings
   - Kernel logs
   - Docker logs
3. Optional time-series panels:
   - Errors over time
   - Warnings over time
4. Useful filtering by host, systemd unit, and syslog identifier.
5. A layout optimized for troubleshooting rather than general metrics monitoring.

The dashboard is based on Loki labels generated by Alloy.

---

## Existing Alloy Configuration

The starting Alloy configuration was:

```alloy
loki.relabel "journal_relabel" {
  forward_to = []

  rule {
    source_labels = ["__journal__systemd_unit"]
    target_label  = "unit"
  }

  rule {
    source_labels = ["__journal_syslog_identifier"]
    target_label  = "syslog_identifier"
  }

  rule {
    source_labels = ["__journal_priority"]
    target_label  = "priority"
  }
}

loki.source.journal "system" {
  forward_to = [loki.write.local.receiver]

  relabel_rules = loki.relabel.journal_relabel.rules

  labels = {
    job  = "systemd-journal",
    host = "ubuntu-laptop",
  }
}

loki.write "local" {
  endpoint {
    url = "http://loki:3100/loki/api/v1/push"
  }
}
```

This creates useful Loki labels including:

- `job`
- `host`
- `unit`
- `syslog_identifier`
- `priority`

---

## Important Journal Priority Mapping

The `priority` label comes from the systemd journal priority value.

|Priority|Meaning|
|---|---|
|0|Emergency|
|1|Alert|
|2|Critical|
|3|Error|
|4|Warning|
|5|Notice|
|6|Informational|
|7|Debug|

For the dashboard:

- `priority="3"` → Errors
- `priority="4"` → Warnings

# Final Row — Log Explorer

Visualization: **Logs**

Recommended query:

{job="systemd-journal", host=~"$host", unit=~"$unit", syslog_identifier=~"$syslog_identifier"}

Recommended settings:

- Sort order: Descending
- Show timestamps
- Show labels
- Wrap lines
- Show common labels where useful

This is the primary troubleshooting panel.

The intended appearance is:

07:51:31  kernel    ...

# Recommended Alloy Improvement

It was recommended to expose a couple of additional journal fields:

rule {

  source_labels = ["__journal__comm"]

  target_label  = "comm"

}

  

rule {

  source_labels = ["__journal__pid"]

  target_label  = "pid"

}

`comm` can be particularly useful for identifying the process that emitted a message.

However, care should be taken with Loki label cardinality.

Recommended stable labels:

job

host

unit

syslog_identifier

priority

comm

Avoid turning highly dynamic values such as arbitrary request IDs, container IDs, or other frequently changing values into Loki labels.

## Final Outcome

The dashboard design uses Loki primarily as a **troubleshooting and log exploration system**, with only a small number of supporting time-series visualizations.

The key design principle is:

> **Stats identify that something is wrong → time series show when it happened → service panels identify where it happened → Log Explorer shows exactly what happened.**

The existing Alloy configuration already provides the essential labels needed for this design. The main remaining validation items are confirming the actual `syslog_identifier` values for kernel and Docker messages and optionally adding `comm`/`pid` metadata.
